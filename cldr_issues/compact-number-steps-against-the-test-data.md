# TR35's compact-number steps give other results than CLDR's test data

TR35's steps for compact number formats, read as they are written, give results that CLDR's test data does not have. CLDR's own test data under `common/testData` is generated from ICU, so this is a place where the specification and ICU differ, and an implementation cannot follow both.

All references are to CLDR `6198cae999ceb4847b25ddc0815835f07fced411`.

## The specification

TR35 Numbers, Compact Number Formats (`docs/ldml/tr35-numbers.md`, from line 441):

> 1. Let P be the pattern element with greatest type less than or equal to N, and any count value.

> 3. If the element value of P is "0", then use the corresponding non-compact number formatting instead, and skip the rest of these steps — but adjust the precision as described below.

> If the value is precisely “0”, either explicit or defaulted, then the normal number format pattern for that sort of object is supplied — either `<decimalFormat>` or `<currencyFormat type="standard">` — with the normal formatting for the locale (such as the grouping separators). However, for the “0” case by default the significant digits are adjusted for consistency, typically to 2 or 3 digits, and the maximum fractional digits are set to 0 (for both currencies and plain decimal). Thus the output would be $12, not $12.01.

## The test data

`common/testData/decimal/decimals_extended_numbers.tsv` and its two companions, generated by `org.unicode.cldr.tool.GenerateDecimalFormatTestData`:

| Locale | Input | Test data | By the steps as written |
|---|---|---|---|
| `en` short | 999999.9 | "1M" | "1000K" |
| `en` short | 999.9 | "1K" | "1,000" |
| `de` short | 999999.9 | "1 Mio." | "1.000.000" |
| `de` short | 999.9 | "1000" | "1.000" |
| `de` short | 5000 | "5000" | "5.000" |
| `en` short | 1.5 | "1.5" | "2" |
| `en` short | 0.00831765 | "0.0083" | "0" |

## What differs

* **The pattern is chosen before the number is rounded.** Step 1 takes the pattern by N, and nothing says to choose again where the rounded number reaches the next type. In `en`, 999999.9 takes the type of 100000, is divided by 1000 and is formatted at two significant digits as "1000K"; in `de`, whose pattern for that type is "0", it is the plain number, "1.000.000". The test data chooses the pattern for the rounded number.

* **The grouping of a number whose pattern is "0".** German's short pattern for 1000 is "0", so 5000 takes "the normal formatting for the locale (such as the grouping separators)", which in German is "5.000". The test data groups a compact number only where two digits come before the separator (ECMA-402's `useGrouping: "min2"`, its default for compact notation).

* **The fraction digits of a number whose pattern is "0".** "The maximum fractional digits are set to 0" writes 1.5 as "2" and 0.00831765 as "0". The test data keeps two significant digits. The sentence also has the significant digits "adjusted … typically to 2 or 3 digits", and does not say which of the two settings governs.

## Suggested fix

Have the steps say what the test data shows: that the number is rounded to the precision before step 1, or that step 1 is done again where rounding changes the type; that compact notation groups by `min2` by default; and that the "0" case keeps two significant digits, its fraction digits not being cut to none.
